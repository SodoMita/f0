Babylon caches compiled programs per engine, keyed by vertex+fragment@defines — but Effect.dispose() deletes the cache entry when the last material using it goes away. We dispose an AssetContainer after every poster render, every live-preview swap and every viewer navigation, so identical models recompiled from scratch every time and only 2 of 14 compiled programs survived a board load. Effect.PersistentMode = true fixes it; the cache is bounded by distinct define sets, not by models.

What each one was

readPixels

Babylon's rtt.readPixels() is a Promise-wrapped synchronous gl.readPixels — a full pipeline sync, ~120 ms per poster. Posters now read back through a PIXEL_PACK_BUFFER + fence (_readPixelsAsync), with the sync call only as a fallback.

Events verified three times

nostr-tools' Relay verifies every matching event itself, then our ingress verified it, then parseModelEvent verified it again (it even deleted the memo first). At ~46 ms of secp256k1 per event, on the main thread. Now: the relay's duplicate check is off, ingress verifies once in an inline worker, and our own results are remembered in a WeakSet.

One decode per model

getModelBytes() shares a single Uint8Array between poster, preview and viewer; validateGLBCached() memoises the limit report by hash; Babylon loads from those bytes instead of a File (which re-reads the whole model through a FileReader).

Mipmaps on repainted textures

Reply badges and loading rings were created with mipmaps, so every repaint re-uploaded and rebuilt the whole mip chain — constantly, while slots recycle during scrolling.

Still standing

texImage2D (~4%) is the poster texture upload, and getProgramParameter (~3%) is Babylon polling shader link status — both are inherent, and both are inflated by the software rasteriser used in CI. The next structural step, if it ever matters on real hardware, is to display the poster render target directly instead of reading it back and re-uploading it as a texture.
