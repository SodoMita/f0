SwiftShader is a software rasteriser, so absolute fps is low by design — the ratios are the signal. Boot and bundle numbers are from the production build; the rest is the dev server with live relay content.

What changed

Render on demand

The loop draws only when kick()ed (input, content arrival, route change — a 300 ms window) or while a registered animation source reports motion, capped at 30 fps. The sources are precise: motion only while a loading-ring step or a live-preview refresh is actually due, a camera really moved, or drag/momentum is running. A static board now renders zero frames.

Virtualised board (also a bug fix)

Card slots are recycled to the rows nearest the viewport. Slots used to be bound by index, so with more roots than slots every row past the 24th was never drawn — you scrolled into empty space. The 48-card stress case exists because of that discovery.

Work follows the viewport

Posters and live previews are requested only inside a one-screen prefetch window, and only once scrolling has settled (150 ms); the poster queue is paused while the feed moves so a GLB parse can't stall a fling. Live previews are capped per slot and skipped entirely for offscreen cards.

Cheaper posters

Straight from the GPU readback to a texture — the PNG for the IndexedDB cache is encoded off the critical path (it used to go pixels → PNG → Image → canvas → getImageData → texture). One reusable 448×280 render target and readback buffer, and 3 warm-up frames + one readback instead of up to 60 readbacks with 100 ms sleeps.

Adaptive resolution — made to actually work

It fed the duration of the render() call into its EMA (~0.9 ms; render() only submits work), so it could never trigger. It now measures the gap between consecutive frames and immediately started doing its job: EMA 80 ms → 0.7× scale during the fling, which is most of the scrolling win. Target ratio = devicePixelRatio clamped by a 2.6 Mpx buffer budget.

Smaller bundle

Curated glTF loader (src/model/gltf.ts): drops the glTF 1.0 loader and KHR_interactivity's FlowGraph engine, which a viewer can never execute.

Two agents, one task

Another agent (kestrel) was working the same performance task in parallel — my miss, it was claimed in STATUS. The merge keeps their engine API (kick() + addAnimationSource() + adaptive resolution) as the single mechanism and layers this branch's work on top, rather than shipping two competing render loops.
